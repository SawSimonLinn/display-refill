# Decision Log

All entries are specification decisions; none imply implemented code.

| ID | Decision | Reason / alternative deferred |
| --- | --- | --- |
| D01 | Supabase Auth is the sole auth system | Shared native/web identity and database access model |
| D02 | SwiftUI iOS; Next.js/TypeScript admin/API | Native capture with desktop configuration |
| D03 | Supabase Postgres/Storage; SQL migrations | One primary backend, no ORM dependency required |
| D04 | Single image + explicit store/display selection | Smaller, testable MVP than AR/video or recognition |
| D05 | Immutable published POG versions | History remains meaningful after layout changes |
| D06 | Rectangular normalized slots with crop alignment | Resolution-independent configuration; no claim of perspective invariance |
| D07 | Vision adapter + durable SQL queue/worker | Provider can change without changing business logic |
| D08 | Backend calculates inclusive-threshold refill | Consistent results across both clients |
| D09 | Unknowns block confirmation; default confidence cutoff 0.80 | Explicit human review; calibrate during pilot |
| D10 | Admin edits shared catalog/POGs; manager assigns to own displays | Prevent accidental cross-store configuration changes |
| D11 | Manual workflow first, online only | Useful baseline with no provider dependency |
| D12 | Confirmed counts immutable; completion is attestation | Preserve evidence and avoid false inventory claims |
| D13 | Light/dark accessible operational UI | Appropriate for bright store environments |
| D14 | npm workspaces, single root lockfile; workspace packages consumed as TS source | Turbopack transpiles them for admin; esbuild bundles the worker. pnpm/Turborepo deferred until build times justify them |
| D15 | iOS app target generated by XcodeGen (`apps/ios/project.yml`); code lives in the `DisplayRefillKit` Swift package | Keeps the hand-edited surface reviewable; generated .xcodeproj is git-ignored |
| D16 | Provisional iOS minimum 17.0 | Store devices not yet checked (no device or Xcode available during feature 01) |
| D17 | Admin config errors do not crash the server; API routes return 503 `CONFIGURATION_INVALID` and the log names variables only. Worker exits 78 | Health stays observable; values are never printed |
| D18 | Health endpoint is public and reports `database: not_checked`, `authentication: not_implemented`, `job_queue: not_implemented` until those exist | Avoids implying capabilities that are not built |
| D19 | shadcn/ui components are added when first needed (feature 04); feature 01 defines tokens with shadcn-compatible names | No unused generated components |
| D20 | Only `VISION_PROVIDER=mock` is accepted until feature 09 | Prevents an unbenchmarked provider being configured by accident |
| D21 | Clients get SELECT-only grants; every write (including admin catalog edits) goes through the API with the service role | One enforcement point for validation, idempotency and audit; RLS policies are read-only |
| D22 | Multi-row trusted functions (`publish_pog_version`, `create_scan`) live in `public`, are executable by `service_role` only, take the API-verified actor as `p_actor`, and re-check membership/tenant rules inside | Callable through the Data API by the server only; clients get 42501. Not user-callable, so the caller-identity rule in code-standards does not apply |
| D23 | Invariants that must hold for every role are triggers, not function logic: publication validation, published immutability, display→published-only, scan/slot history guards, append-only tables, last active admin | A UI or service bug cannot bypass them; verified as service role and database owner |
| D24 | RLS helpers are `SECURITY DEFINER` functions in the unexposed `private` schema with `search_path = ''` | Avoids recursive policies; not callable through the Data API |
| D25 | Layout visibility: admins see all org versions incl. drafts; managers (in any org store) see the org catalog and published versions; employees see versions assigned to their stores' displays or pinned by their stores' scans, and those versions' products | Matches the permission matrix "relevant active layout data" |
| D26 | Errors from trusted functions/triggers use the API error code as the Postgres message (NOT_FOUND, FORBIDDEN, CONFLICT, VALIDATION_FAILED, POG_NOT_ASSIGNED, POG_CHANGED, IMMUTABLE, LAST_ADMIN) with a safe detail | The API maps them without parsing free text. Cross-tenant access returns NOT_FOUND |
| D27 | Public signup disabled in local config (`[auth] enable_signup = false`); test identities are created through the Auth admin API with random, unstored passwords; seed contains no users | Matches invite-only auth and "no plaintext passwords in seeds" |
| D28 | Local container runtime: Colima (headless) instead of Docker Desktop | Already-installed Homebrew; any Docker-compatible runtime works |
| D29 | Feature 02 ships exactly two trusted transactional functions: `publish_pog_version` and `create_scan` (the spec's "publish and scan snapshot functions"). Count saving and confirmation (06/07), completion (07), upload finalize and enqueue (08), job claim/lease/result (09), corrections and manual takeover (10), and membership changes (03) each arrive with their feature, with the same service-role-only grant pattern and a catalog test that keeps clients from executing them | Each needs domain logic owned by its feature (e.g. refill arithmetic for confirmation). Their tables, constraints, append-only triggers and frozen-after-confirmation guards already exist, so client roles cannot write them in the meantime |
| D30 | API and web verify every access token with Supabase Auth (`auth.getUser(token)`, i.e. `GET /auth/v1/user`), then read memberships through a caller-scoped client | Local JWKS verification (`getClaims`) accepts a token after sign-out until it expires; a negative control proved it (the logout test failed with `getClaims`). Cost: one Auth request per API call |
| D31 | iOS talks to Supabase Auth's HTTP endpoints (`/auth/v1/token`, `/auth/v1/logout`) through `SupabaseAuthClient`, behind the `SupabaseAuthAPI` protocol, instead of supabase-swift | SwiftPM cannot resolve or link packages on this machine and Xcode is absent (E01/E02). Same identity system and endpoints the SDKs use; swap the implementation once the toolchain works |
| D32 | Invite acceptance and password-reset completion happen on the web: email link → `/auth/confirm` (GET shows a button) → `POST /auth/verify` (server-side `verifyOtp` with token hash) → `/account/password`. iOS starts a reset through `POST /api/v1/auth/password-reset`, then signs in normally. No mobile deep-link callback in MVP | One allowlisted redirect (`APP_ORIGIN/auth/confirm`), tokens never in URL fragments or redirect targets, link scanners cannot consume tokens with GET. Works from a phone browser |
| D33 | Invitations only create new identities; an email that already has an account returns 409 | Avoids silently attaching an existing person to another organization. Reveals existence of the email to an org admin only (authenticated, rate-limited) |
| D34 | Web sessions use httpOnly, SameSite=Lax cookies written only by the server; there is no browser Supabase client. Auth forms are plain POSTs to route handlers that require `Origin == APP_ORIGIN` (or `Sec-Fetch-Site: same-origin`). Cookie-authenticated `/api/v1` mutations require the same check; bearer requests do not | Covers login CSRF, forced logout and cross-site API writes; works without JavaScript |
| D35 | Membership writes go through service-role-only functions `apply_membership_invite` and `update_membership` (audited). `stores` in a PATCH is the complete active assignment set. The organization membership `revision` covers the whole assignment. `POST /members/invite` and `PATCH /members/:user_id` require `Idempotency-Key` | One transaction per change with before/after audit; retries are safe; last-admin trigger now locks the organization row (A02) |
| D36 | A caller with no active organization membership gets 403 on every `/api/v1` route; on the web, employees and revoked users go to `/no-access` | Revocation is visible immediately and distinctly from an expired session (401) |
| D37 | Password minimum 12 characters (app validation and local Auth config); invite/reset/sign-in/invite-sending rate limits are in-process fixed windows | Pilot defaults. Multi-instance hosting needs a shared limiter (feature 12) |
| D38 | First admin is provisioned only by `scripts/bootstrap-admin.mjs` → `bootstrap_first_admin` (service role), which refuses an organization that already has an active admin and requires `--confirm-remote <host>` for non-loopback projects | Satisfies "operator-only bootstrap; never first user becomes admin" and cannot be used to take over an organization |
| D39 | Store, product, POG identity and display writes go through service-role-only functions (`create_/update_store`, `_product`, `_pog`, `_display`) that resolve organization/store from the stored row, re-check the actor, require `expected_revision` on updates (409 when stale), write audit events in the same transaction, and report the offending request field in the Postgres HINT (mapped to `field_errors`) | Same pattern as D22/D35. A field name in HINT keeps validation messages specific without parsing text |
| D40 | Store numbers are unique per organization, compared case-insensitively; a duplicate is 422 `field_errors.store_number`, not 409 | It is an invalid field value the user can fix in place; 409 stays reserved for revision/state/idempotency conflicts |
| D41 | Archive, never delete: stores/displays/products `active=false`, POGs `archived=true`; archived POG versions cannot be newly assigned; a display can only be restored in an active store; the display's store never changes | Preserves history and keeps scans' references valid; matches data-model lifecycle rules |
| D42 | Lists are oldest-first over `(created_at, id)` with an opaque base64url cursor, `status=active|archived|all`; archived rows are listed only to their org admins and the store's managers, and employees asking for them get 403 | Matches the cursor convention; filters never expand RLS visibility |
| D43 | Dashboard edit forms send only the fields the user changed (plus `expected_revision`); after a 409 the user reloads, untouched fields show the newer server values and edits are kept | Found in the browser pass: sending the whole form after a reload would silently revert another person's change to an untouched field |
| D44 | shadcn/ui is still not installed (revises D19); feature 04 forms are small app components on the existing semantic tokens | No generated components were needed; revisit with the feature 05 editor |
| D45 | Integration tests that write data use organizations created per run; seed organizations A/B are only read or used as "another organization" in denials | DB/API files share one database and the feature 02/03 suites assert exact seed sets; found when the full suite ran (progress tracker) |

| D46 | POG reference bytes use an authenticated exact-path API upload endpoint, ten-minute actor-bound intent, private staging path, then write-once content-addressed canonical JPEG | Supabase signed upload tokens have a fixed two-hour TTL; API upload enforces current access and the intended expiry. Different concurrent crops cannot overwrite a winning image |
| D47 | One open draft per POG, serialized next-version allocation at draft creation; published clone shares reference and creates fresh slots | Revision-checked slot-set saves make authoring atomic without changing published assignments/history |
| D48 | Canonical reference: EXIF upright, optional quarter turn, selected normalized crop, metadata stripped, max long edge 2048; slot coordinates use six decimals, crop min edge 64 px | Browser scaling/letterboxing is independent of camera perspective. Numeric percentages expose all rectangle values |
| D49 | Draft conflict recovery preserves local layout and requires explicit whole-layout override; override is refused if the reference changed | POG slot-set saves intentionally replace a whole layout. Feature 04 forms retain field-specific PATCH behavior; an unseen new reference cannot reuse coordinate approval |
| D50 | Failed concurrent reference outputs and replaced draft images wait for safe unreferenced cleanup in Feature 12 | Deleting an output during an in-flight finalization can delete another request’s winner; shared cloned references require reference-aware retention |

## Feature 08 Decisions (2026-10-03)
| ID | Decision | Reason |
| --- | --- | --- |
| D57 | Scan photos use the Feature 05 authenticated exact-path API upload pattern, not Supabase's fixed two-hour upload token. Ten-minute actor-bound intents may be renewed while a pending scan is less than 24 hours old | Enforces current Auth/membership, expiry, byte limits and no overwrite; safe recovery keeps the original photo |
| D58 | Staging `capture.jpg` is promoted to `validated-{sha256}.jpg`. Finalization applies EXIF orientation, physically crops the upright display bounds, strips metadata and scales to 2048. Stored crop metadata records the original upright source dimensions and crop plus validated output dimensions | Concurrent different crops cannot replace a winning image; workers only read immutable validated pixels, with slot coordinates relative to that canonical crop |
| D59 | Photo creation and finalize replay/enqueue are owned by one service-only transaction. Photo requests require expected POG, expected finalize revision and stable keys; authorization precedes every replay | Pins the displayed layout and closes response-loss/duplicate-job windows |
| D60 | Feature 08 queues validated photos but returns `analysis_available:false`; iOS explicitly offers a separate manual check and has no processing spinner/poll loop | Feature 09 owns workers/providers; no fabricated results or indefinite processing promise. Manual takeover remains Feature 10 |
| D61 | Pending photo bytes, crop and exact mutation bodies/keys are stored in account/display-scoped, protected cache files and removed on sign-out. Cache eviction or a 24-hour abandoned scan requires retake | Process/background recovery without promising durable offline sync. No signed reference links are persisted |

## Feature 09 Decisions (2026-10-03)
| ID | Decision | Reason |
| --- | --- | --- |
| D62 | Queue functions `claim_scan_job`, `heartbeat_scan_job`, `finish_scan_attempt` are service-role only and own the lifecycle constants in SQL: 90 s lease, two live leases per store (per-store transaction advisory lock), three provider attempts per generation, 5 s then 20 s backoff plus up to 25% jitter, Retry-After honored up to 300 s. Locks are always scan row, then job row | One authoritative budget across worker processes; a store at capacity is skipped while other stores continue; consistent lock order prevents claim/finish/takeover deadlocks |
| D63 | One fenced finish function records attempt evidence (latency, sanitized usage, input hash/dimensions, normalized response) **before** checking the lease token, job state, generation and `processing` status. A stale holder's attempt becomes `superseded` (or keeps `timeout`/`cancelled`); job/scan changes require the current lease. Success recomputes `review_required` in SQL from the normalized values and refuses any result that does not cover exactly the pinned slots, carries a known count under uncertain/poor alignment, or has extra fields | Duplicated billing after worker death is visible; duplicated or late accepted results are impossible. A worker bug cannot downgrade review routing |
| D64 | Feature 09 delivers the transactional manual-takeover and explicit-retry functions plus `POST /scans/:id/manual-takeover` and `POST /scans/:id/retry`. Takeover increments the generation before cancelling jobs, marks in-flight attempts `cancelled`, resets accepted counts to unknown/pending, sets source `manual` while keeping the image (new `scans_image_source_check`) and expires a pending upload intent. Retry adds a generation only for failed photo scans with a retained image, at most two per scan | Feature 09's acceptance requires demonstrating takeover fencing and the documented retry budget. Feature 10 keeps the iOS takeover action and AI-comparison review UI |
| D65 | Scan detail adds `analysis {generation, failure_code, retry_available, retries_remaining, alignment, image_flags, provider, synthetic, manual_takeover_at}` from new `scans.failure_code`/`ai_summary`/`manual_takeover_*` columns. Attempts, usage and lease data stay service-only. Photo creation now returns `analysis_available: true`; health reports `job_queue: not_checked` (D18: the queue now exists but is not probed) | Clients poll one RLS-scoped read; failure is a persisted code, not a provider message. `synthetic` lets the app label mock output honestly |
| D66 | Only the deterministic mock adapter is selectable (`VISION_MOCK_SCENARIO`: mixed, good, poor_alignment, occluded, invalid, duplicate_ids, unknown_id, missing_slot). No real provider is selected: that still needs the small benchmark and data-handling review in the Feature 09 spec | Avoids sending store photos to an unreviewed provider; every review/failure path is exercisable offline |
| D67 | Stored usage keeps only non-negative integer counters (`input_tokens`, `output_tokens`, `total_tokens`, `image_count`, `cost_usd_micros`). Provider/storage errors are reduced to stable codes (`PROVIDER_RATE_LIMITED`, `PROVIDER_UNAVAILABLE`, `PROVIDER_NETWORK`, `PROVIDER_CONFIGURATION`, `PROVIDER_REJECTED`, `PROVIDER_TIMEOUT`, `INVALID_OUTPUT`, `INVALID_SLOT_IDS`, `IMAGE_UNAVAILABLE`, `IMAGE_INVALID`, `ANALYSIS_TIMEOUT`); logs carry IDs and codes only | Provider messages and metadata can echo keys or signed URLs |
| D68 | iOS polls GET scan every 2 s for five polls, then 3, 4 and 5 s; stops outside queued/processing; stops when backgrounded or leaving the screen and resumes by scan ID. After 30 s it shows "taking longer than usual" with the manual option. Needs-review shows only a server-derived summary (estimated/unknown/needs-verification counts, alignment and quality flags, synthetic label); AI estimate review/confirmation stays Feature 10 | Matches scan-lifecycle.md client recovery without inventing progress or letting unreviewed estimates be confirmed through the manual UI |
